# Agent SDK API Service 设计方案

> 基于当前仓库内 `scripts/demo_single_turn.py` 和 `scripts/demo_multi_turn.py` 的能力，收敛为一套统一、可演进的服务端设计。

## 1. 设计目标

- 统一单轮与多轮能力，避免两套平行实现长期分叉
- 会话 ID 完全使用 Claude Agent SDK 原生 `session_id`
- 文件上传与会话能力解耦，支持任意轮次上传文件
- 所有运行参数统一从 `conf/*.yaml` 读取，不在代码中写死
- FastAPI 仅作为 HTTP 薄层，Agent 逻辑尽量收敛在独立模块

## 2. 当前 Demo 的结论

### 2.1 `scripts/demo_single_turn.py`

- 证明了 `query()` 方式可用于无状态单次执行
- 适合一次性任务，如代码审查、问答、摘要
- 问题是它把单轮执行建成独立接口，和多轮实现重复了配置、消息解析、错误处理

### 2.2 `scripts/demo_multi_turn.py`

- 证明了 `ClaudeSDKClient` 可支持会话和文件上传
- 当前脚本自行生成了 `sess_xxx`，这与 SDK 原生会话机制不一致
- 上传文件目录与会话标识绑定方向是对的，但绑定对象应为 SDK `session_id`

### 2.3 收敛结论

- 单轮和多轮不是两种服务，而是同一条消息处理链路的两种使用方式
- 文件上传不是多轮专属能力，单轮请求同样可以上传文件
- 正式实现不再区分 `single_turn` / `multi_turn` 两个接口模型

## 3. 核心设计决策

### 3.1 会话 ID 来源

- `session_id` 由 Claude Agent SDK 生成
- 服务端不创建业务侧 session 主键
- 服务端只负责透传、缓存和基于 `session_id` 管理附属资源

依据：

- SDK `ClaudeAgentOptions` 支持 `continue_conversation` 与 `resume`
- SDK 的 `TaskStartedMessage`、`ResultMessage` 均可返回 `session_id`

### 3.2 接口模型

采用一个统一消息接口：

- `POST /v1/agent/messages`

请求字段：

- `prompt`: 必填
- `session_id`: 可选，不传表示新会话
- `files[]`: 可选，支持任意轮次上传

接口语义：

- 不传 `session_id` 时，SDK 创建新会话，服务端从 SDK 消息中提取并回传 `session_id`
- 传入 `session_id` 时，服务端通过 `resume=session_id` 恢复会话
- 是否继续多轮由客户端决定，而不是由接口区分

### 3.3 配置方式

- 运行配置统一存放在 `conf` 目录下的 YAML 文件
- 代码启动时加载 YAML，生成结构化配置对象
- `model`、`allowed_tools`、`system_prompt`、`upload_root`、服务端口等参数均不写死在 Python 文件中

## 4. 配置设计

建议先使用单一主配置文件：

```text
conf/
  config.yaml
```

推荐配置内容：

```yaml
app:
  host: 0.0.0.0
  port: 8000
  reload: true

sdk:
  base_url: http://localhost:4000
  api_key: sk-1234
  model: claude-sonnet-4-5
  max_turns: 25
  continue_conversation: true
  permission_mode: acceptEdits
  setting_sources:
    - project
    - user
  allowed_tools:
    - Read
    - Write
    - Edit
    - MultiEdit
    - Bash
    - Skill
    - Glob
    - Grep
    - WebSearch

agent:
  system_prompt: >
    你是一个专业、严谨的工程师 Agent。
    优先使用 Skill 指导流程，结合用户 prompt 给出有用建议。

storage:
  upload_root: uploads
  cleanup_on_shutdown: false

api:
  return_steps: true
  max_step_preview_chars: 800
```

后续如需拆分配置，再演进为：

```text
conf/
  app.yaml
  agent.yaml
  storage.yaml
  logging.yaml
```

## 5. API 设计

### 5.1 统一消息接口

**Endpoint**

```http
POST /v1/agent/messages
Content-Type: multipart/form-data
```

说明：

- 为了同时支持文本和文件，统一采用 `multipart/form-data`
- 无文件时也可以仅提交表单字段

**请求参数**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `prompt` | string | 是 | 用户输入 |
| `session_id` | string | 否 | SDK 生成的会话 ID，不传表示新建会话 |
| `files` | file[] | 否 | 用户上传文件，图片、PDF、代码文件均可 |

**响应体**

```json
{
  "session_id": "sdk-generated-session-id",
  "final_answer": "分析结果...",
  "steps": [
    {
      "type": "AssistantMessage",
      "content": "..."
    }
  ],
  "success": true
}
```

### 5.2 对外接口

仅暴露 `POST /v1/agent/messages`（`multipart/form-data`），不再提供单独的 JSON `/run` 路径，避免双入口分叉。

## 6. 会话与文件处理流程

### 6.1 新会话，无文件

1. 接收 `prompt`
2. 构造 `ClaudeAgentOptions(continue_conversation=True)`
3. 发起 SDK 请求
4. 从 `TaskStartedMessage.session_id` 或 `ResultMessage.session_id` 获取 SDK 会话 ID
5. 返回 `session_id` 与最终答案

### 6.2 新会话，有文件

1. 接收 `prompt + files`
2. 文件先保存到临时目录
3. 发起 SDK 请求并获取 SDK `session_id`
4. 将临时目录归档到 `upload_root/<session_id>/`
5. 将保存后的文件名拼接进 prompt，引导 Agent 使用 `Read`
6. 返回 `session_id` 与最终答案

### 6.3 续接会话，无文件

1. 接收 `prompt + session_id`
2. 构造 `ClaudeAgentOptions(resume=session_id, continue_conversation=True)`
3. 发起 SDK 请求
4. 返回同一个 `session_id` 的新结果

### 6.4 续接会话，有文件

1. 接收 `prompt + session_id + files`
2. 将文件保存到 `upload_root/<session_id>/`
3. 构造包含文件引用的 prompt
4. 使用 `resume=session_id` 继续会话
5. 返回结果

## 7. 文件上传策略

### 7.1 目录规则

- 上传根目录由 `conf/config.yaml -> storage.upload_root` 决定
- 会话目录使用 SDK `session_id` 作为目录名
- 建议结构：

```text
uploads/
  <session_id>/
    image-1.png
    spec.pdf
    notes.txt
```

### 7.2 安全要求

- 对上传文件名做清洗，避免路径穿越
- 同名文件需要重命名或追加唯一后缀，避免覆盖
- 限制单文件大小与总上传大小
- 仅允许保存到配置指定的上传目录

### 7.3 Prompt 拼接策略

当请求包含文件时，服务端在原始 prompt 前补充文件清单，例如：

```text
用户上传了以下文件：image-1.png, spec.pdf

<原始 prompt>

请先使用 Read 工具读取这些文件，然后按要求回复。
```

## 8. SDK 调用策略

### 8.1 单次执行

无论是新会话还是续接会话，都走统一执行流程：

- 构造 `ClaudeAgentOptions`
- 调用 SDK
- 收集 `AssistantMessage`
- 解析 `TaskStartedMessage` / `ResultMessage` 中的 `session_id`
- 统一返回 HTTP 响应

### 8.2 `ClaudeAgentOptions` 约束

这些字段来自 YAML 配置：

- `model`
- `allowed_tools`
- `permission_mode`
- `max_turns`
- `setting_sources`
- `system_prompt`
- `cwd`

这些字段来自请求上下文：

- `resume`
- `continue_conversation`

建议规则：

- 新会话：`continue_conversation=True`，`resume=None`
- 续接会话：`continue_conversation=True`，`resume=<sdk session_id>`

## 9. 服务端模块拆分

建议结构：

```text
agent-sdk-api-service/
├── conf/
│   └── config.yaml
├── main.py
├── src/
│   ├── __init__.py
│   ├── config.py
│   ├── api/
│   │   ├── __init__.py
│   │   ├── models.py
│   │   └── routes.py
│   ├── agent/
│   │   ├── __init__.py
│   │   ├── options.py
│   │   └── executor.py
│   └── storage/
│       ├── __init__.py
│       └── file_store.py
└── scripts/
    ├── demo_single_turn.py
    ├── demo_multi_turn.py
    └── demo_chat_client.py
```

### 9.1 `src/config.py`

职责：

- 读取 `conf/config.yaml`
- 提供结构化配置对象
- 设置 SDK 所需环境变量，如 `ANTHROPIC_BASE_URL`、`ANTHROPIC_API_KEY`

### 9.2 `src/agent/options.py`

职责：

- 根据 YAML 配置构造 `ClaudeAgentOptions`
- 根据请求上下文决定是否注入 `resume=session_id`

### 9.3 `src/agent/executor.py`

职责：

- 调用 SDK
- 统一解析消息流
- 提取 `final_answer`
- 提取 SDK `session_id`
- 收集调试 `steps`

### 9.4 `src/storage/file_store.py`

职责：

- 保存上传文件
- 文件名清洗与去重
- 管理会话目录
- 提供生成文件提示文本的辅助方法

### 9.5 `src/api/routes.py`

职责：

- 定义 FastAPI 路由
- 处理表单请求
- 调用 `file_store` 与 `executor`
- 输出标准响应

## 10. 与现有 Demo 的关系

### 10.1 `scripts/demo_single_turn.py`

保留价值：

- 作为最小执行链路 demo
- 用于验证 `query()` 的基础调用方式

后续定位：

- 不作为正式 API 实现来源
- 可保留为独立 smoke test 示例

### 10.2 `scripts/demo_multi_turn.py`

保留价值：

- 作为统一消息接口的原型基础
- 证明文件上传和会话链路可行

需要修正：

- 去掉项目自造 `session_id`
- 不再维护业务侧 `SESSION_STATES` 作为主会话源
- 上传目录改为基于 SDK `session_id`

### 10.3 `scripts/demo_chat_client.py`

保留价值：

- 可作为 `/v1/agent/messages` 的本地调用示例
- 适合验证“首次上传文件 + 后续继续提问”的典型链路

## 11. 推荐实现顺序

### 第 1 阶段

- 新增 `conf/config.yaml`
- 实现 `src/config.py`
- 实现统一 `ClaudeAgentOptions` 构造逻辑

### 第 2 阶段

- 实现 `src/agent/executor.py`
- 统一解析 SDK 消息并提取 `session_id`
- 完成 `POST /v1/agent/messages`

### 第 3 阶段

- 实现 `src/storage/file_store.py`
- 支持新会话与续接会话的文件上传
- 完成上传目录与文件名安全策略

### 第 4 阶段

- 将 `main.py` 接入新模块
- 将 `scripts/demo_chat_client.py` 改为调用新接口
- 将两个 demo 降级为样例脚本

## 12. 最终结论

本项目正式版应采用以下原则：

- 只保留一条统一消息处理链路
- `session_id` 只使用 SDK 原生会话 ID
- 文件上传与单轮/多轮完全解耦
- 所有运行参数统一来自 `conf` 目录下的 YAML 配置
- FastAPI 负责协议层，Agent 逻辑下沉到独立模块

这套设计能覆盖当前两个 demo 的能力，同时避免后续演进时出现三套配置、两套接口、两套会话模型并存的问题。
